## Logic Flow & Question Format Specification

This section accounts for the new variable question formats and branching introduced in Chapter 1.

### Question Object Schema

Each question is one of three types: `standard`, `branching`, or `narrative_consequence`.

```ts
type Question =
  | StandardQuestion
  | BranchingQuestion
  | NarrativeConsequenceQuestion;

interface StandardQuestion {
  id: string;                    // "q1", "q2", etc.
  type: "standard";
  scene: string;                 // narrative setup text
  prompt: string;                // the actual question
  illustration?: string;         // SVG/image asset path, optional
  choices: Choice[];             // 2 to 5 choices supported
}

interface BranchingQuestion {
  id: string;
  type: "branching";
  scene: string;
  prompt: string;
  illustration?: string;
  branches: {
    label: string;               // "Fight", "Run"
    nextQuestionId: string;      // "q6a", "q6b"
    icon?: string;
  }[];
}

interface NarrativeConsequenceQuestion extends StandardQuestion {
  type: "narrative_consequence";
  // After selection, show a consequence message before advancing
  consequenceTemplate: (choiceId: string) => string;
}

interface Choice {
  id: string;                    // "a", "b", "c", "d", "e"
  label: string;                 // what the user sees
  characterRef?: string;         // optional, for character-specific choices
  weights: [number, number];     // [Δx, Δy]
}
```

### Question Flow Sequence

Questions are no longer a flat array of 12. They form a directed graph because of Q6's branching:

```
Q1 → Q2 → Q3 → Q4 → Q5 → Q6 ─┬─ Fight → Q6A → Q7 → Q8 → Q9 → Q10 → Q11 → Q12
                              │
                              └─ Run → Q6B → [consequence beat] → Q7 → Q8 → Q9 → Q10 → Q11 → Q12
```

Total questions answered by any user: **always 12 scoring questions**, regardless of branch. Q6 is a free routing decision (no weight); the weighted scoring happens in Q6A or Q6B.

### Progress Bar Logic

Because Q6 branches but always returns to a single flow, the progress bar represents *scoring questions answered*, not absolute position in a tree. Math:

```
progressPercent = (scoredQuestionsAnswered / 12) * 100
```

Q6's binary fight-or-run choice does NOT count toward the 12 — it's a routing prompt. Q6A and Q6B both count as question 6 in the progress.

### Branching Question UI

The branching screen (Q6) looks different from a standard question:
- No 4-choice grid
- Two large parallel buttons, full visual weight on each
- Each button has its own visual treatment (icon, color hint)
- Selection triggers a transition that signals you're committing to a path

Once you advance from Q6, the next screen (Q6A or Q6B) looks like a standard question again.

### Consequence Beat Logic (Q6B specifically)

After the user selects who to leave behind in Q6B, the app shows a brief consequence message before advancing to Q7:

1. User selects choice in Q6B (e.g., "Leave Jennifer behind")
2. Choice's weights are recorded
3. Screen transitions to a half-screen narrative card: *"Plot twist: Jennifer also escaped on her own. She's alive. She's fine. She's just never going to let you forget this."*
4. User taps "continue" or auto-advances after 4 seconds
5. Transition to Q7

This pattern is reusable for future consequence beats in later chapters.

### Variable Choice Count Handling

Questions can have 2, 3, 4, or 5 choices. The UI must handle all cases gracefully.

**Mobile layout rules:**
- 2 choices: stacked vertically, large tap targets, ~50% screen height
- 3 choices: stacked vertically, slightly smaller cards
- 4 choices: stacked vertically (preferred) or 2×2 grid if landscape
- 5 choices: stacked vertically, scrollable if needed, slightly compressed card height

**Desktop layout rules:**
- 2 choices: side-by-side or stacked (designer call)
- 3 choices: vertically stacked or horizontal row
- 4 choices: 2×2 grid
- 5 choices: 2×3 grid with last cell empty, OR vertical list (designer call)

Cards within a question are always the same size as each other — never mix big and small choices within one screen.

### Scoring Algorithm Update

Same as v1 but tolerant of variable question counts via the branching path:

```js
function calculateScore(answers) {
  let rawX = 0;
  let rawY = 0;

  for (const answer of answers) {
    // skip routing questions (e.g., Q6 fight-or-run)
    if (!answer.weights) continue;
    rawX += answer.weights[0];
    rawY += answer.weights[1];
  }

  // Theoretical max is now slightly higher due to weight range
  // (some answers in Q2 are [+2, +2] = magnitude ~2.8 each)
  // Normalize against actual max possible
  const MAX_RAW = 24; // tune based on highest-magnitude path through the tree
  const normalizedX = Math.max(-5, Math.min(5, (rawX / MAX_RAW) * 5));
  const normalizedY = Math.max(-5, Math.min(5, (rawY / MAX_RAW) * 5));
  const magnitude = Math.sqrt(normalizedX ** 2 + normalizedY ** 2);

  return { x: normalizedX, y: normalizedY, magnitude };
}
```

### Chapter Versioning

This is **Chapter 1**. Future chapters will reuse the same engine but ship as new question sets. Each profile can be optionally tagged with a chapter or default to "latest." The data model should support this:

```sql
-- future addition (not in current schema, for reference)
alter table profiles add column chapter int not null default 1;
```

Or chapters can live entirely as client-side data files (`chapters/chapter1.ts`, `chapters/chapter2.ts`) — recommended for v1 since chapter content is static and authored content, not user data.
